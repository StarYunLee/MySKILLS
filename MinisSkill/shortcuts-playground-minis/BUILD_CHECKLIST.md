# Build Checklist

## 作用

在开始生成前，确认是否已经具备足够信息进入构建。

## 必查项

| 检查项 | 需要确认的内容 | 不清楚时的处理 |
|---|---|---|
| 目标 | 用户真正要完成什么 | 先澄清 |
| 入口 | 手动运行、分享菜单、小组件、自动化 | 先澄清 |
| 输入 | 文本、URL、图片、文件、上下文数据 | 先澄清 |
| 落点 | 系统应用、第三方应用、文件、URL、分享面板 | 先澄清 |
| 写入方式 | 新建、写入固定对象、先选对象 | 先澄清 |
| 顺序 | 核心动作的先后顺序 | 先澄清 |
| 完成后行为 | 结束、提示、打开目标、继续下一步 | 先澄清 |
| Hybrid 接受范围 | 纯快捷指令、URI/第三方动作、Minis/外部服务 | 先澄清 |

## 构建前判断

### 可以直接进入构建

同时满足：

- 目标明确
- 输入明确
- 落点明确
- 顺序明确
- 完成后行为明确

### 必须先停下来澄清

满足任一项：

- 落点不明确
- 写入方式不明确
- 顺序不明确
- 完成后行为不明确
- 是否接受外部依赖不明确

## 输出要求

### 信息充分时

先输出一行流程摘要：

```text
我理解的流程：A → B → C → D
```

### 信息不足时

改用固定选项式澄清：

```text
1. 问题1
• A：回答1
• B：回答2
• C：回答3
• D：回答4

推荐流程：A → B → C
可直接复制确认：按推荐流程补齐上面问题的选项后执行。
```

## 使用原则

- 这份清单用于判断“能不能开工”，不是用于描述实现细节
- 缺失项只要会改变路线，就必须先问
- 若缺失项只影响默认值，可声明默认值后继续
