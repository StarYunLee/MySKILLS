# Routing Framework

## 目标

把自然语言任务先转成**任务规格**与**实现路线**，再决定是否生成快捷指令 XML。

## 标准任务规格

在开始写 XML 前，先把需求归一化成这组字段：

- `goal`：用户真正想完成什么
- `trigger`：手动运行、分享表单、桌面、小组件、Siri、自动化
- `input`：文本、URL、图片、文件、位置、时间、剪贴板、分享输入、无输入
- `transform`：拼接、提取、判断、循环、格式化、过滤、联网请求、文件处理
- `output`：显示、通知、保存、追加、分享、打开、发送、调用别的 App
- `destination`：系统应用、文件、URL Scheme、第三方动作、外部服务
- `permissions`：位置、照片、提醒事项、备忘录、网络、文件访问等
- `dependencies`：目标 App、插件、URL Scheme、API、Cookie、登录态
- `interaction`：全自动、少量交互、多步交互
- `runtime`：前台短任务、可接受跳转、是否允许外部网络
- `delivery_mode`：仅草稿、验证后交付、完整签名交付

如果这些字段还不清楚，不要直接写 XML。

## 实现路线优先级

默认按以下顺序选实现路线：

1. **原生 WorkflowKit 动作**
2. **已文档化 AppIntent**
3. **稳定 URL Scheme / x-callback-url**
4. **已验证第三方 Shortcuts 动作**
5. **Minis 命令增强（查阅 `MINIS_CAPABILITIES.md`）** ← 新增
6. **混合执行：快捷指令 + Minis / 外部服务**
7. **不建议做成快捷指令，改为 Minis 直接执行**

## 何时优先做成快捷指令

适合 Shortcut-native 的任务通常有这些特征：

- 前台短流程
- 用户交互明确
- 系统已有动作支持
- 输出目标是提醒事项、备忘录、照片、分享、通知、URL、文件等常见对象
- 联网逻辑简单，通常只需 `Get Contents of URL` 与基础 JSON 处理
- 对浏览器登录态、Cookie、复杂网页渲染依赖较低

## 何时优先做成混合流程

适合 **Hybrid** 的任务通常有这些特征：

- 快捷指令负责入口、交互、分发
- Minis 负责复杂下载、网页处理、签名、文件转换、脚本执行
- 需要借助第三方签名服务或远程服务
- 用户仍希望最终以快捷指令作为可复用入口

**Minis 命令增强**是 Hybrid 的子集，仅在用户明确提到「用 Minis」「走 Minis」「Minis 能做吗」时触发。此时查阅 `MINIS_CAPABILITIES.md` 定位工具：
- AI 感知（OCR、图像分类、人脸检测、NLP、语音识别）
- 健康数据（HealthKit 查询/写入）
- 智能家居（HomeKit 控制/场景）
- 网页交互（浏览器截图、内容提取、表单填写）
- 媒体处理（照片导出/导入、音乐控制）
- 系统交互（剪贴板、设备信息、通知）

## 何时不应强行做成快捷指令

以下情况默认先考虑 Minis 直接执行，而不是强行拼 Shortcuts：

- 需要复杂网页抓取、浏览器登录态、Cookie、反爬绕过
- 需要长时间后台任务或大量文件处理
- 依赖不稳定的网页结构或私有接口
- 主要工作是 shell、Python、下载器、转码器、爬虫
- 生成快捷指令只会增加维护成本，而不能明显提升复用价值

这类任务若用户仍想要快捷指令，优先做 **launcher / hybrid shortcut**，不要假装全都能纯 Shortcuts 完成。

## 动作规划顺序

先按阶段拆任务，再映射动作：

1. **输入获取**：Ask / Share Sheet / Clipboard / Choose / Date / URL
2. **上下文准备**：变量、字典、默认值、分支条件
3. **核心处理**：文本处理、过滤、HTTP 请求、列表、循环、判断
4. **结果落点**：提醒事项、备忘录、文件、URL、通知、分享、第三方 App
5. **收尾动作**：显示结果、确认信息、打开目标、分享产物

不要先想 XML 细节，先把动作链讲清楚。

## 失败降级顺序

当某条路线证据不足或实现成本过高时，按顺序降级：

1. 原生动作 → AppIntent
2. AppIntent → URL Scheme
3. URL Scheme → 第三方动作
4. 纯快捷指令 → 混合执行
5. 完整成品 → 先出草稿 / 已验证 XML
6. 自动完成 → 最小必要澄清

## 最小澄清规则

当自然语言描述**模糊、缺边界、缺默认落点、缺交互方式**时，必须先进入澄清，而不是直接生成 XML。

只有在这些信息缺失时才问用户：

- 缺少目标应用或落点，导致动作路线完全不同
- 缺少必要环境信息，如默认目标标识、默认提醒事项列表名、第三方应用目标参数、API key
- 是否接受第三方服务会直接改变签名或实现路线
- 不同理解会导致产物行为明显不同
- 输入方式不明确，例如是手动输入、分享输入、剪贴板、URL 还是文件
- 写入方式不明确，例如是新建、追加、覆盖、选择现有对象，还是写入默认对象
- 运行方式不明确，例如是手动点按、桌面图标、分享菜单、小组件或自动化触发

### 澄清策略

- 先给出一版**最小规格草案**，再提出关键问题。
- 问题只允许覆盖会改变实现路线的歧义，不要把可默认的信息都变成问答。
- 若存在稳定默认值，可先声明默认假设并继续；若默认假设会明显改变用户体验，则必须先问。
- 若目标对象存在多种合理解释，优先把候选边界列出来让用户选，而不是替用户拍板。
- 澄清问题默认使用固定选项式模板，不使用自由散文式追问。
- 问题数量按关键歧义数量决定，不人为限制为固定 1~3 个。
- 每个问题的选项数量按问题本身决定，不强制固定为 3 个。
- 提问后必须附一版推荐流程，并提供一条可直接复制确认的文本。

### 固定提问模板

```text
1. 问题1
• A：回答1
• B：回答2
• C：回答3

2. 问题2
• A：回答1
• B：回答2
• C：回答3
```

### 提问后的推荐流程输出

在问题后补两段：

1. **推荐流程**：给出当前最推荐的一条实现路线。
2. **可直接复制确认**：给出用户可直接回复的一行文本。

格式示例：

```text
推荐流程：A → B → C
可直接复制确认：按推荐流程：1A、2B、3C。
```

### 必须先问、不能直接生成的典型场景

- “记到备忘录里”——未说明是新建笔记、追加到固定笔记，还是每次选择笔记
- “加到提醒事项”——未说明默认列表、标题格式、是否需要时间/日期
- “发到第三方应用”——未说明目标对象、写入参数、是否已装插件或 URI 能力
- “下载某平台视频”——未说明是否接受 Hybrid、第三方服务、网页登录态或外部依赖

其他信息优先用合理默认值推进。

## 执行模式

- `draft-only`：只输出 XML 草稿
- `build-and-validate`：输出草稿并完成本地验证
- `full-delivery`：生成、验证、签名、交付成品

默认：
- 初次设计复杂任务时，先 `build-and-validate`
- 用户明确要最终文件时，再 `full-delivery`

## 结果评估

在说“这个任务可以做成快捷指令”前，至少确认三件事：

- 路线是否清晰
- 关键动作是否有依据
- 最终落点是否可交付

如果三者只满足前两项，应表述为“可先出草稿/可先验证”，不要直接说成品可交付。
